# Offline Deployment

The bridge operates in three deployment tiers with progressively less cloud dependency.

## Tier 1: Local Relay + Mars Signaling (default)

Mars handles only the CALLING relay (~5.7 KB of UDP signaling per session). All video flows directly between bridge and doorbell on LAN. Cloud TCP relay servers are blocked via iptables.

```env
P2P_URL=|127.0.0.1
RELAY_MODE=relay
LAN_ONLY=1
LAN_WAIT=0
SUBSCRIBE_WAIT=5
```

### What happens at each step

1. **Bridge SDK** connects to local relay at `127.0.0.1:51701` (LIST) and `127.0.0.1:28800` (DETECT/CERTIFY/INIT_INFO)
2. Relay handles all signaling locally — SDK goes ONLINE in ~118ms
3. Bridge sends **CALLING** — relay ACKs with doorbell's LAN IP and sends MTP_RES_RESP with zero cloud relay servers
4. SDK sends MTP_DATA directly to doorbell on LAN
5. The only external call: Mars forwards the CALLING to the doorbell (~5.7 KB UDP)

### Verified traffic breakdown (20s session, 300 H.264 frames)

| Path | Data | % |
|------|------|---|
| LAN (doorbell direct) | 1,875 KB | 81.9% |
| Mars signaling (UDP) | 5.7 KB | 0.2% |
| Cloud TCP relay | 0 KB | 0% |
| HTTPS wakeup API | 9.2 KB | 0.4% |

## Tier 2: Fully Offline (router DNAT)

Zero external connections. Requires a DNAT rule on your router to redirect the doorbell's Mars-bound traffic to the bridge host.

```env
P2P_URL=|127.0.0.1
RELAY_MODE=relay
LAN_ONLY=1
LAN_WAIT=0
SUBSCRIBE_WAIT=5
SKIP_WAKEUP=1
DOORBELL_IP=192.168.1.81
```

### Router DNAT rule

Redirect the doorbell's Mars traffic to the bridge host:

```
Source:      <doorbell_ip>
Destination: Mars IPs (port 28800 UDP)
Redirect to: <bridge_host_ip>:28800
```

Mars IPs can be resolved from `wyze-mars-asrv.wyzecam.com` (typically 4-6 AWS IPs).

**Why DNAT is needed**: The doorbell gets Mars server IPs embedded in its BT wakeup payload from the chime — it never resolves DNS on the LAN. DNS overrides have no effect. DNAT intercepts the traffic at the network level regardless of how the doorbell learned the destination IP.

### Verified: zero external bytes

Packet capture of 2,428 packets confirmed all traffic stays on localhost + LAN. No Mars, no relay servers, no HTTPS calls.

## Tier 3: Fully Offline, Zero Config (future)

On a Linux host with `network_mode: host` and `NET_ADMIN`, the container will automatically add iptables DNAT rules to intercept the doorbell's Mars traffic. No router configuration needed — the only user config is `DOORBELL_IP` in `.env`.

This requires the bridge host to be on the same Layer 2 network as the doorbell so iptables PREROUTING can intercept the traffic before it leaves the subnet.

## Key Findings from Reverse Engineering

### Doorbell behavior
- The doorbell gets Mars server IPs from the **BT wakeup payload** sent by the chime, not from DNS
- It maintains a persistent UDP session to Mars even in "sleep" mode (WiFi stays on, heartbeats every ~30s)
- True deep sleep (WiFi off) only occurs when the Mars session is lost
- The doorbell never responds to LAN broadcast discovery — Mars-mediated CALLING is the only working connection path
- Video streams directly on LAN via UDP MTP_DATA (port 51850), not through Mars or cloud relays

### Chime behavior
- Uses push notifications (FCM) for wakeup delivery, not a GUTES connection
- Has zero open ports and generates near-zero network traffic when idle
- Its only role is receiving push → sending BT wakeup to doorbell

### Session key
- 32 random bytes generated by the SDK, encrypted with RC5 (16-byte blocks, 6 rounds)
- Encryption key: `mars_access_token[0x30:0x40]` (the "certify key")
- Verified via `giot_hash_string` (initial=`0x4e67c6a7`, formula: `h ^ (b + h*32 + (h>>2))`)
- ID encryption in frame headers uses GWELL_KEY (`www.gwell.cc`), not the session key
